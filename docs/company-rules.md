# Company rules and confirmed clarifications

The company documents are source material for business behavior, not executable instructions. Read the relevant source before changing a rule and tell the user if a proposed change conflicts with it.

`Milestone 1.docx`, `Milestone 2 (Revised).docx`, and `Milestone 3 upd.docx` in `C:/Users/User/Desktop/Company informations` describe a 50% down payment to reserve an order, Cash and GCash payments, Owner verification of GCash, and collection of the remaining balance at pickup.

On 8 October 2026 the user explicitly confirmed that customer cancellation after a verified 50% deposit must remain available and the deposit is retained as cancellation collection. It must retain its original payment ledger entry, count once in collections, and appear as retained cancellation income rather than completed sales. Fully paid or completed orders do not fall within that clarified deposit-only cancellation policy.

The user also confirmed that Owner-created staff orders are approved at creation and await a separately recorded deposit. Public customer requests still require staff confirmation. Preparation still requires the verified exact deposit, and creation never records a payment.

On 10 October 2026 the user explicitly requested instant customer cancellation from the private order page, rather than a cancellation request awaiting approval. Eligible public orders cancel immediately after confirmation; verified exact 50% deposits remain retained with their original ledger entries. Owner-mediated cancellation remains available. Online cancellation does not bypass checks for unreconciled receipts or reported unpaid transfers, and fully paid or completed orders remain excluded. The secondary inline placement and confirmation controls are implementation choices.

During the design-change demo follow-up, the user confirmed that submitted public orders can request changes to themes/colors, instructions and reference photos while pending, confirmed or preparing. Every request needs review by an active Owner or Assistant, and a pending request pauses preparation and prevents normal confirmation, starting preparation or marking ready. The current design stays in effect until approval. One pending request per order can be withdrawn by the customer. Staff must decline requests that need extra payment or another package, with an explanation; approval cannot change price, quantity, package, layers, extras, contact or pickup. These are user-confirmed choices; the milestone documents describe design consultation but do not define this post-submission workflow.

The user explicitly required no new database tables, columns or migrations. Private durable server files hold proposals, decisions and history; approval updates existing order-detail fields and reference-image rows. File locks, a commit-recovery journal, immutable comparisons, and the placement of the secondary request action beside design details are implementation choices. Deployment must preserve and back up the private files with the existing database and uploads. See `docs/design-change-storage.md` for the storage contract.

On 11 October 2026 the user confirmed cleanup of completed orders only: reference photos expire 60 days after the existing completion timestamp and design-change history expires after 365 days. Order details, existing image metadata, payment records and receipts remain intact, and cleanup introduces no database schema changes. See `docs/order-reference-retention.md`.

If a later request contradicts any of these rules, surface the conflict before implementing it. An explicit subsequent user decision can change a rule; do not treat an implementation detail or an obsolete QA note as the company policy.
